# 병렬화 전략 (설계 메모)

> Claude가 생성한 설계 메모. 구현 전 방침 정리이며 실측에 근거한 것은 아님.
> 수치 추정(스레드 수 등)은 N/K/L로부터 산출한 설계값.

## 1. 병렬화의 2계층

```
그리드    : 배치 B개의 서명    → blockIdx.x = 서명 인덱스
블록      : 1 서명의 내부 연산  → threadIdx.x = 계수/레인
```

- **확정 방침:** 1 서명 = 1 스레드블록.
- 블록 내 스레드 수는 NTT 한 단계를 협력 처리할 수 있는 규모로 상정(예: 128 또는 256).
  N=256이므로 스레드 1개 = 계수 1~2개.

## 2. 각 단계의 병렬 적합성

| 단계 | 주요 연산 | GPU 적합성 | 비고 |
|------|----------|:---:|------|
| keygen | 행렬 A 전개 (SHAKE), s1/s2 샘플, t=As1+s2, NTT | ◯ | SHAKE 전개가 순차적이나 계수 생성은 병렬 |
| sign | y 샘플, w=Ay, 분해, 챌린지 c, z=y+cs1, **reject 판정** | △ | rejection sampling이 warp divergence 주원인 |
| verify | c 복원, w' 재구성, hint 적용, 해시 비교 | ◯ | 반복 없음. 배치 검증은 무난히 병렬 |

## 3. NTT (가장 중요한 커널)

- N=256의 NTT를 1 블록에서 수행.
- 버터플라이 연산을 단계마다 `__syncthreads()` 로 동기화.
- 트위들 인자는 `__constant__` 메모리에 배치.
- K+L = 15개의 다항식 벡터에 대해 반복 적용.

## 4. rejection sampling 처리 (최대 난제)

- 서명은 "z, r0, ctilde, hint가 모든 조건을 만족할 때까지" 반복. 반복 횟수는 입력 의존이라 불정.
- 1 서명 = 1 블록이면 **블록 간** 반복 횟수 차이는 그리드가 흡수
  (먼저 끝난 블록은 종료, 느린 블록이 율속).
- **블록 내부**는 모든 스레드가 같은 반복에 있으므로 divergence 최소.
- 대안: reject된 서명만 모아 재투입하는 compaction 방식(향후 검토).

## 5. SHAKE / Keccak

- Keccak-f[1600]은 24라운드 순차. 1 permutation 내 병렬도는 제한적(25 레인).
- 방침: 우선 1 스레드가 1 SHAKE 인스턴스를 돌리고 **배치 병렬**로 지연을 은닉.
- 최적화 여지: fips202x4 상당의 다중 인스턴스 동시 처리(avx2 구현이 참고 대상).

## 6. 메모리

- 키·서명 버퍼는 배치 분량을 device 측에 연속 할당하고, H2D/D2H를 1회로 묶음.
- 다항식 계수는 int32. 다항식 1개 = 256 × 4B = 1KB. 중간 버퍼는 블록당 (K+L+…)개.
- shared memory에 NTT 작업 영역을 둘 수 있는지 검토 필요(블록당 다항식 개수 × 1KB가 한도 내인지).

## 7. 검증 흐름

1. 고정 시드로 GPU keygen → CPU 참조 keygen과 키 일치 확인.
2. GPU sign → CPU 참조 verify 통과 확인(서명은 난수 의존이라 값 일치가 아니라 검증 성공으로 판정).
3. NIST KAT (META의 nistkat-sha256)과 대조.
